feat(updater)!: the app chooses the request headers sent to another origin with the required `autoUpdater.crossOriginHeaders` property: `(headerNames: string[], hop: { from: URL; to: URL }) => string[]` (the `CrossOriginHeadersCallback` and `CrossOriginHop` types), `null` by default. electron-updater calls it for each request and redirect to another origin than the update feed (`Provider.feedBaseUrl`; private GitHub's feed is the GitHub API): a redirect, a download or channel file on another origin, a blockmap or differential range request and their redirects, a private GitHub release asset or GitLab release link on another origin, and a provider's own request there. It gets the lowercase names of the request headers about to be sent, never their values, and returns the names of the ones to send (case-insensitive); the feed's origin gets every header without it. A header it leaves out stays on the original origin: `Authorization` from `addAuthHeader`, a custom header from `requestHeaders`, a provider's token (private GitHub, GitLab), a provider's other request headers and `x-user-staging-id`. The headers electron-updater builds for each request itself are sent whatever it returns: its default `User-Agent`, `Cache-Control`, the `Accept` it or the provider sets, and `Range`; an app's own `User-Agent` from `requestHeaders` goes to another origin only when it keeps `user-agent`. `autoUpdater.crossOriginHeaders = () => []` sends none of the app's headers to another origin. Without a function, `checkForUpdates()`, `checkForUpdatesAndNotify()` and `downloadUpdate()` emit `error` and reject with `ERR_UPDATER_CROSS_ORIGIN_HEADERS_NOT_CONFIGURED`, whose message names the property and links the migration guide, and so does each request to another origin, such as one of the install at launch of an update marked for the next launch: set it before the app is `ready`. An unpackaged app without `forceDevUpdateConfig`, which skips the check, gets the same error from `checkForUpdates()` and `checkForUpdatesAndNotify()`, so a missing callback shows up in development. A throw, or a result that is not an array of strings, fails that request, unsent, with `ERR_UPDATER_INVALID_CROSS_ORIGIN_HEADERS`. builder-util-runtime: `HttpExecutor` takes a `CrossOriginHeaderPolicy` (`(headers, hop) => headers`) for its redirects as its constructor argument, by default electron-builder's, which leaves out the credential-bearing headers (see `addSensitiveRedirectHeader`); `HttpExecutor.crossOriginHeaders(headers, ownHeaders, hop, policy)` applies one, and `ApiRequestOptions.ownHeaders` and `DownloadOptions.ownHeaders` name the headers a request builds itself, which a hop to another origin sends whatever the policy keeps. electron-updater's `ProviderRuntimeOptions` has a required `crossOriginHeaderPolicy`, set by electron-updater, so code that constructs a built-in provider passes on the runtime options it was given. See https://www.electron.build/docs/migration/v27-runtime-changes#cross-origin-headers The first time a request to an origin goes without some of the app's or a provider's headers, electron-updater logs a warning, once per origin, naming those headers and both origins (never a value), with a link to the migration guide. A `Host` header is never sent to another origin. A provider constructed with runtime options without a `crossOriginHeaderPolicy` function throws `ERR_UPDATER_CROSS_ORIGIN_HEADER_POLICY_MISSING`.
