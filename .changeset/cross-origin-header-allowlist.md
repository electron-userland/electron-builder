feat(runtime)!: a redirect to another origin, and an electron-updater download or channel file request on another origin than the feed, send only the request headers that two layers choose for that request: the update provider's `Provider.crossOriginHeaders(defaults, request)` and the app's `crossOriginHeaderAllowlist`. `checkForUpdates(options)` and `checkForUpdatesAndNotify(options)` require `{ crossOriginHeaderAllowlist }` for every app (`CheckForUpdatesOptions`, and `CheckForUpdatesAndNotifyOptions` with an optional `notification`), either a list of header names or a callback (the `CrossOriginHeaderAllowlist` type). A list (case-insensitive, copied and checked when the check starts) replaces the default list as what the provider gets, and the provider decides last: pass `{ crossOriginHeaderAllowlist: DEFAULT_CROSS_ORIGIN_HEADERS }` (exported by electron-updater) for the default list (`Accept`, `Accept-Encoding`, `Accept-Language`, `User-Agent`, `Cache-Control`, `Pragma`, `Range`, `If-Range`, `If-Match`, `If-None-Match`, `If-Modified-Since`, `If-Unmodified-Since`, `Content-Type`, `Content-Length`, `Content-Encoding`, `Content-Language`), or `[...DEFAULT_CROSS_ORIGIN_HEADERS, "x-tenant"]` to add one; with a built-in provider the list is exactly what is sent, and private GitHub still sends every header (its token too) to the GitHub API's origin. A callback comes after the provider: it gets the provider's choice as `defaults` (the names of every header of the request when the provider returns `null`) and the request (`{ from, to, kind: "redirect" | "request" }`), and returns the header names for that request, or `null` for every header on it. `x-user-staging-id` goes to another origin only when allowed. A call without the option, or with a value that is neither a list nor a function, and `downloadUpdate()` before such a check, reject with `ERR_UPDATER_CROSS_ORIGIN_HEADERS_NOT_CONFIGURED`; a list entry that is not a header name rejects the check with `ERR_UPDATER_INVALID_CROSS_ORIGIN_HEADERS`, naming its index; replace `checkForUpdatesAndNotify(notification)` with `checkForUpdatesAndNotify({ crossOriginHeaderAllowlist, notification })`. Every provider implements `crossOriginHeaders` (abstract): the built-in providers return `defaults`, and private GitHub returns `null` for the GitHub API's origin and `defaults` elsewhere; a provider without it fails the update check with `ERR_UPDATER_CROSS_ORIGIN_HEADERS_NOT_CONFIGURED`, naming it, before any request (see https://www.electron.build/docs/migration/v27-developer-changes#custom-provider-cross-origin-headers). `Provider.feedBaseUrl` only fills `request.from`: without a feed URL, `from` is `null` and both layers are asked about every request. Both are asked only for another origin (for every request without a feed URL); for a redirect the updater follows, the provider is the one of the latest check, and the app's allowlist of the last check also serves its download and the install of an update marked for the next launch. A throw or a result that is not an array of header names or `null`, from the provider or the app's callback, fails that request with `ERR_UPDATER_INVALID_CROSS_ORIGIN_HEADERS`, naming the layer. builder-util-runtime exports `DEFAULT_CROSS_ORIGIN_HEADERS` and the `CrossOriginRequest` (`from: URL | null`), `CrossOriginHeadersCallback` and `CrossOriginHeadersLayer` types (the first three re-exported by electron-updater, with `CrossOriginHeaderAllowlist`); `HttpExecutor` takes a `CrossOriginHeadersCallback` as its constructor argument for its redirects (`crossOriginRedirectHeaders()` returns what they use), `HttpExecutor.keepCrossOriginHeaders(headers, request, crossOriginHeaders)` applies one or an array of layers, and builder-util-runtime has no `addSensitiveRedirectHeader`, `HttpExecutor.removeCrossOriginSensitiveHeaders` or `HttpExecutor.sensitiveHeaderNames`. See https://www.electron.build/docs/migration/v27-runtime-changes#cross-origin-header-allowlist
