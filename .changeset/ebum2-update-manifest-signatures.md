feat!: EBUM2 update manifest signatures cover every field. `latest*.yml` is now signed in a second payload format, `EBUM2`: the manifest as canonical JSON (keys sorted at every depth, no whitespace) with every top-level field except `signature`, `signatures`, `releaseName` and `releaseNotes`. A field added to the manifest later is signed without any verifier change, and adding, changing or removing any covered field — `releaseDate`, `vendor`, `files[].blockMapSize` and `files[].isAdminRightsRequired` included — invalidates the signature. electron-builder dual-signs: each key writes an `EBUM1` entry (which electron-updater 7.0.0-alpha.8 to alpha.12 verify; they ignore the new `format` tag) followed by an `EBUM2` entry, and the YAML is read back and checked against what was signed. electron-updater prefers `EBUM2`, verifies the manifest as published (before a provider adds `tag`, `assets` or a feed release name), and accepts an `EBUM1` signature only for a manifest whose top-level fields are all ones an `EBUM1`-only electron-builder writes, so a newer field cannot be smuggled in by stripping the `EBUM2` signatures. A manifest signed only with `EBUM1` that carries any other top-level field is now refused with `ERR_UPDATER_MANIFEST_SIGNATURE_INVALID` naming the field; rebuild it with this electron-builder. A value that does not survive YAML as itself (a `Date` in `releaseInfo.vendor`, for example) fails the build. Adds `canonicalizeForSigningV2`, `UpdateManifestSignatureFormat` and the optional `signatures[].format` to builder-util-runtime, `serializeSignedUpdateManifest` and a `format` parameter on `signUpdateManifest` to builder-util, and exports `parseUpdateInfo` / `carryUpdateManifestSource` from electron-updater for custom providers.
